# Failure handling

Every row says how the failure is **detected**, how it's **handled**, what **users see**, and where it's **verified** (automated test, bench scenario, or the in-app Chaos mode).

| # | Failure | Detection | Handling | What users see | Verified by |
|---|---|---|---|---|---|
| 1 | **Client network drops** (Wi-Fi blip, laptop lid) | Client: socket `close`, or no `pong` for 9 s (watchdog for half-open sockets). Server: no protocol pong for 2 × 7 s. | Client reconnects with exponential backoff + jitter (0.25 s → 5 s) and immediately on the browser `online` event. Sends `hello{token, lastSeq}`. The server **replays exactly the missed events** from a 600-event ring, or sends a full snapshot if the client is too far behind. | Amber "Reconnecting… your seat is saved" banner, then "Reconnected — caught up on N missed updates". Others see a dimmed 📡 seat. | `reconnect-storm` bench (20+ drops, 0 lost / 0 duplicate messages), `room.test.ts › resumes…`, Chaos → *Drop connection* |
| 2 | **Messages typed while offline** | `send()` while not connected | Idempotent types (chat, votes, polls, queue edits, reactions to messages) go into an **outbox** and replay on reconnect. The server **dedupes chat by client id**, so retries never duplicate. Playback commands are **dropped, not replayed**: a 20-second-old "pause" is a bug, not intent. | Messages appear once, a moment late. A playback press while offline shows "You're offline — reconnecting…". | `room.test.ts › chat retries… idempotent`, `reconnect-storm` |
| 3 | **Server crash / restart** | All sockets close | Rooms are snapshotted to `data/rooms.json` (every 5 s and on shutdown, atomic tmp + rename). On boot they're restored with every member given a full grace window. The clock is epoch-based, so **the playback anchor stays valid**: clients that kept playing locally resume seamlessly. | Brief reconnect banner, then the chat line "Server restarted — welcome back! Playback continued right where it was." | `room.test.ts › persistence`; observed live during development (`tsx watch` restarts) |
| 4 | **Host leaves or disconnects** | Explicit leave, or the host offline for > 15 s | Host passes to an online **co-host**, else the longest-present member. The old host is demoted to co-host if they come back within the 30 s seat grace. | 👑 toast "X is now the host" and a chat line | `room.test.ts › hands host…`, `› prefers a co-host` |
| 5 | **Someone is buffering** (slow connection) | Client reports `buffering` after 400 ms of `waiting`/`readyState < 3`. The server requires > 1.2 s. | **Strict** policy: the room auto-pauses ("Waiting for Ben…"), then resumes everyone with a short synced countdown once they're ready. Holds are **bounded to 10 s**; after that the slow member is released for 60 s and catches up on their own. **Relaxed** policy: never pause, they catch up via the ladder. Members within 10 s of (re)loading **never** trigger a hold, so late joiners don't pause the room. | Banner with a 10 s progress bar; ⏳ on the seat | Manual (observed live); server logic in `room.ts › checkHold` |
| 6 | **Late join** | `hello` without a token | The snapshot carries the anchor, so the client computes where the room is *now*, loads the media, seeks to `expected + learnedSeekLead` and plays. **Nobody else is affected.** | "Catching up with the room…" overlay for a second | Live browser test (late joiner at −26 ms in about 3 s) |
| 7 | **Concurrent conflicting commands** | Room actor processes messages serially; each carries `baseVersion` | Same-intent commands collapse (second pause = no-op, both credited). Conflicting ones: last arrival wins, flagged `concurrentWith`. Every state has a monotonically increasing `version`, and clients ignore stale versions. Playlist edits use **item-id anchors** (`move X after Y`), never indexes. | ⚡ "Ana and Ben acted at the same moment — went with Ben's (latest)" | `concurrent-actions` bench (12/12 rounds identical), `room.test.ts › collapses…`, `› racing seeks…`, `› playlist moves…` |
| 8 | **Clock skew / wrong system time** | n/a, by design | All timing is on the server clock via NTP-style offsets. Client click times are **clamped** to `[now − 1 s, now]` (and never before the previous change), so a skewed or forged clock can't move the timeline. | Nothing | `room.test.ts › clamps forged / skewed click times` |
| 9 | **Background tab / laptop sleep** | `visibilitychange`; big jump in the estimated offset | Instant clock-sync burst plus an immediate correction step when visible again. Offset jumps > 25 ms are adopted immediately rather than smoothed. | Nothing (it just snaps back) | Manual |
| 10 | **Autoplay blocked by the browser** | `play()` rejects with `NotAllowedError` | Fall back to **muted** playback (stays in sync) and show "Tap to unmute". Entering through the invite gate is itself a user gesture that unlocks audio. | Yellow "Your browser muted autoplay — tap to unmute" pill | Manual (refresh a room tab without clicking) |
| 11 | **Media fails for one person** (codec, embed disallowed, 404) | Adapter `error` event or load timeout (30 s / YouTube 20 s) | Only that member is flagged. They get **Try again** or (if allowed) **Skip for everyone**. YouTube "embedding disabled" errors are translated into plain words. | Error card on their screen, ⚠ on their seat for everyone else | Manual |
| 12 | **Different local files** (local-file mode) | Fingerprint (size + head/tail hash) mismatch | Warn: "isn't the same file — scenes may not line up". The member can pick another or knowingly use it anyway. The room shows who's matched. | Picker with "N of M ready: …" | Manual |
| 13 | **Two tabs with the same seat** | Second `hello` with the same token | The older connection is closed with 4002 "Session opened in another tab". The newest one owns the seat. | Old tab shows the closed state | Code path in `room.ts › join` |
| 14 | **Spam / floods** | Per-connection token bucket (40 msg/s, burst 120) plus per-type buckets (chat 1.5/s, reactions 8/s, commands 6/s) | Excess is dropped with a friendly toast. A connection exceeding the global limit for long is closed (4008). Reactions are batched into 100 ms frames server-side, so a reaction storm costs O(rooms), not O(users²). | "Whoa, slow down a little 🙂" | Code review; bench never trips it |
| 15 | **Malformed / malicious messages** | zod schema validation at the gateway; 64 KB frame cap | Rejected with an `error{code}`; the room never sees it. URLs must be http(s) or `/media/…`. YouTube ids are regex-checked. Chat is rendered as text (no HTML injection). | Nothing (or a warning toast) | Schema in `shared/protocol.ts` |
| 16 | **Outdated client after a deploy** | `hello.v ≠ PROTOCOL_VERSION` | Fatal error with a **Refresh** button | "Marquee was updated — please refresh the page." | Code path in `gateway.ts` |
| 17 | **Wrong / missing passcode, full room, kicked** | `join()` checks | Clear fatal screens. A kicked member's token is banned for the room. | Passcode prompt / "Room is full (50 people)" / "Show's over for you" | `room.test.ts › kicked members cannot rejoin` |
| 18 | **Out-of-order delivery in our own network simulators** | Found by the bench (versions diverged at 25+ users) | Chaos mode and the bots now use a strict FIFO `DelayQueue` (separate `setTimeout`s with equal deadlines can fire out of order). | — | `sync.test.ts › DelayQueue`, `wifi-50` bench |
| 19 | **No microphone access** (plain-http LAN link, permission denied) | `window.isSecureContext` is false, or `getUserMedia` rejects | Join voice in **listen-only** mode: peer links still form and you hear everyone, you just can't talk. A toast explains why and points to the https "Anywhere" link. | "Talking needs the https 'Anywhere' link… You can still listen." | Browser test (2 tabs on http LAN: 1/1 links connected, no mic prompt) |
| 20 | **A voice link fails** (NAT, network change) | `RTCPeerConnection.connectionState === 'failed'` | Close the link and let the member with the smaller id rebuild it after a 3 s back-off. ICE candidates that arrive before the remote description are buffered. | Voice pill shows `connected/expected` links | Code path in `voice.ts`; signalling relay covered by `room.test.ts` and `npm run e2e` |
| 21 | **Voice user's socket drops** | Room `detach` | The server marks them out of voice so peers tear down. On reconnect the client sees itself marked `off` and re-announces, and links rebuild automatically. | Mic badge disappears briefly, then returns | `room.test.ts › relays WebRTC signalling…` |
| 22 | **Pointer / hover floods** | Per-member token buckets (pointer 40/s, hover 12/s, signalling 60/s) | Excess frames are dropped silently: they're presence data, the next frame supersedes them, and nothing is ever replayed. | Nothing | Unit tests plus gateway budget |

## Chaos mode: break it on purpose, live

Open **Sync Lab** (`S`) as host and tap any member:

* **Lag / Jitter** presets add symmetric delay to that member's link (server-side, both directions, order-preserving).
* **Nudge 0.6 s**: knocks their player slightly out of sync. You can watch the drift sparkline glide back via playbackRate (no visible jump).
* **Knock 4 s**: forces a hard-seek recovery.
* **Drop connection**: kills their socket. Watch the 📡 seat, the auto-reconnect, and the replayed events.

Every chaos action is announced in chat, for transparency.
